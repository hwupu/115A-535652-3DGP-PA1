# The Boomerang Guardian, a Report on AI Tools and Scrum

Pu-Hsuan Wu · NYCU 535652 3D Game Programming · Programming Assignment 1 · Unity 6000.3.25f1 LTS with URP · github.com/hwupu/115A-535652-3DGP-PA1

## 1. Use of AI Tools

The project was developed in Unity 6000.3.25f1 LTS with the Universal Render Pipeline over six days in October 2026. The main AI tool was Claude Code running Claude Opus 5.5, an AI agent that works in the terminal with direct access to the project folder, git, the GitHub command line tool and the batch mode of Unity. A second AI agent assisted the developer in rigging and animating the witch character in Blender and handed over a written document that described every animation clip. The role of the AI agent was split in two. It first acted as Scrum Master and turned the 100 mark rubric into a traceable product backlog, and it then acted as programming assistant, while the developer acted as Product Owner as well as asset, scene and sound designer.

The AI agent wrote all C# code of the game, 35 files with roughly 3,000 lines of gameplay logic and 2,000 lines of Editor tooling, together with step by step guides for the work inside the Unity Editor. Every major design decision was recorded as an Architecture Decision Record, eleven in total, and every significant interaction was summarised in a prompt log of 24 entries. From the second sprint on, the AI agent also wrote Editor setup scripts that create prefabs, link components and build the HUD and the minimap automatically. Scene integration that took the developer 45 to 60 minutes by hand in the first sprint took about ten minutes in the second.

The greatest benefit was speed. The complete core loop of spawning, selection by ray casting, boomerang flight, hit physics, scoring and the platform trigger was built and play tested within a single day, which left time for the Halloween theme, an animated character, real sound effects and demonstration features such as a trajectory preview and an orbit camera. Documentation grew during development instead of afterwards. The AI agent also caught process risks, for example by keeping a Unity Asset Store skybox out of the public repository for licensing reasons, and it asked clarifying questions instead of guessing. An ambiguous rule in the specification about respawning objects became a runtime setting in `config.json`, so either interpretation can be shown to the TA.

The limitations were real. The AI agent cannot see or play the game, so every question of feel and appearance depended on the play tests of the developer. Some problems were introduced by the AI agent itself. A silent fallback in its code hid a missing camera reference for two sprints, so the character always moved along the world Z axis. Replacing models broke references to the replaced objects twice, and one field was wrongly marked as optional, which hid an error from the checking tool of the agent. The animation handoff from the Blender agent also stated an incorrect character height.

AI output was therefore never accepted on trust. Every change was compiled by Unity in batch mode inside a copy on write clone of the project, so the open Editor was never disturbed. Setup scripts were run twice to prove that the second run changed nothing. Automated checks included a spawn test of 330 objects with zero overlapping pairs measured by `Physics.ComputePenetration`, a headless run of the built macOS application and a wiring validator that scans the scene and all prefabs for missing references. The animation handoff was tested against a real import before any code relied on it, and every sprint ended with the developer testing each function step by step against a checklist mapped to the rubric.

## 2. Adoption of Scrum

Scrum was adapted to a solo project. The developer held the role of Product Owner, and the AI agent held the roles of Scrum Master and development team. All artifacts lived in the repository, namely a product backlog with a priority and the rubric marks for each item, a Definition of Done, a traceability matrix from rubric lines to backlog items, and one document per sprint with the plan, a daily log, the review and the retrospective. GitHub Issues, milestones and a Project board mirrored the backlog, as shown in Figure 2.

Sprint 0 set up the repository with Git LFS, the backlog, the decision records and the board. Sprint 1 delivered a walking skeleton with the bounded arena, camera relative movement, the speed toggle, jumping and both camera views. Sprint 2 delivered the core loop, from the spawn manager and selection by ray casting to the boomerang, hit physics, the platform trigger, collectibles, the HUD and the runtime configuration. Sprint 3 added the minimap, the Hero's Journey story with seven stages and the first macOS build. Sprint 4 handled polish requested by the Product Owner, including a movement bug and the wiring validator, and Sprint 5 brought the Halloween art, the animated witch, real sound, ghost effects, the hover trajectory preview and a middle mouse orbit camera for the demonstration.

The board and the sprint structure broke the assignment into small and focused tasks, and every review against the traceability matrix showed which rubric marks were still open. Retrospectives produced real changes. One retrospective led to the automatic scene setup scripts, and a later one introduced code that fails loudly together with automated wiring checks. When the second sprint finished on its first day, the plan was changed from three to five sprints so that logic polish came before art. The main challenges were that story points lost their meaning with an AI agent writing the code, so they were dropped, that requirements such as Git LFS, licensing rules and the theme kept emerging, and that one checklist item was once marked as passed while a bug was still present.

## 3. Reflection

The project taught the developer how to build a Unity game with an AI native approach while following a Scrum workflow, from the first backlog to the final build.

AI assisted development proved extremely helpful. Its output was never trusted blindly, and every function was tested step by step, yet the time it saved allowed the developer to focus on creativity.

The board, the sprints and the retrospectives helped a great deal even in a solo project, because they broke the work into tasks and kept the development focused on its mission. The retrospectives mattered most. As a result of one, the developer and the AI agent created scripts in the second sprint that set up the Unity scene automatically, which saved time and removed manual errors.

In a future project, the developer would add more visual effects such as particle systems and put more focus on creativity to make the game more fun to play.
